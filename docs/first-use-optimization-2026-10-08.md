# 首次解析优化记录

## 定位与范围

项目面向刷到喜欢的抖音作品后临时打开网页、粘贴分享文案、解析一次并保存的用户。本轮优先减少首次请求开销，保留作者、封面、背景音乐、画质及图文和实况资源；不新增重复作品缓存，不修改解析并发、重试次数或完整性条件。

既有网页通过跨域 JSON POST 调用 Worker，浏览器需要先发送 OPTIONS。本轮改用 `URLSearchParams` 表单提交，保持正常可读取的 CORS 响应，不增加代理层。标准允许满足条件的 URL 编码表单 POST 直接发送，见 [MDN CORS 文档](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)。

## 实现与兼容

- Worker 保留 JSON，新增 `application/x-www-form-urlencoded`，统一进行 32 KiB 请求体、5000 字符输入、HTTPS、域名及限流检查。拒绝重复的表单 `url` 字段。
- 网页使用浏览器生成的表单 Content-Type，不添加自定义请求头，也不携带凭证。首次解析无需先访问健康接口或预热请求。
- 表单编码过长时直接提交 JSON，保留原有长分享文案的可提交范围。新网页连接旧 Worker 收到 HTTP 415 时仅回退一次 JSON，取消、限流和其他失败不触发该回退。
- 成功响应字段及解析、下载流程保持一致。发布应先更新 Worker，再更新前端；旧 Worker 回退路径仍会产生预检和一次额外的 415 请求，不是优化后的性能基线。

## 本地验证

- 正常 Windows 环境运行 `npm run check`：格式、ESLint、113 项测试、前端构建及前后端类型检查通过。沙箱中的 Vitest 首次执行遇到临时转换文件不可读取，改为正常环境执行后通过。
- 3 个真实样本分别进行修改前后各 3 次测试，共 18 次；均成功。普通视频每次 2 个上游 fetch，L1 每次 14 个上游 fetch，资源及元数据存在性保持一致。
- Node 入口真实上游测试的修改前 / 后中位数：V1 为 399 / 358 ms，V3 为 430 / 438 ms，L1 为 8170 / 7870 ms。这些是不同时间的上游采样，不能据此归因性能提升；主要改动发生在浏览器请求链路。
- 实际浏览器访问 `127.0.0.1:5173`，跨端口请求 `127.0.0.1:8787`，V3、L1 均直接发送一个 POST，无 OPTIONS；页面保留作者、音乐、下载入口及完整性提示。点击到结果约 0.85 / 10.91 秒，包含自动化观察开销，不代表生产速度。
- 浏览器实际保存 L1 动态优先 ZIP 和原图 ZIP，分别包含 3 个 MP4、3 个 JPEG。FFprobe 识别动态轨为 960×720 H.264/AAC、约 3.93 秒；静态图为 1920×1440、1920×1440、2880×2160。FFmpeg 对全部 6 个文件完整解码通过。
- 浏览器实际保存 V3 普通视频，FFprobe 识别为 1440×2560 HEVC/AAC、约 10.83 秒，FFmpeg 完整解码通过。

## 发布与线上对照

线上对照使用 V1、V3、L1，每个样本 2 轮，顺序请求间隔 8 秒。修改前显式测 OPTIONS + JSON POST，修改后测表单 POST；这是模拟首次请求链路，真实浏览器的预检复用及用户网络可能不同。必须同时记录版本、边缘节点及各阶段时间，不预先承诺固定提升比例。

本地验证完成，线上发布与对照结果将在完成后补充。

## 验收边界

已覆盖两个普通视频和一个实况图文，尚未覆盖独立纯图集样本、超过 64 MiB 的普通视频及手机真实保存。桌面浏览器保存与文件解码通过不能替代手机相册验收；上游时延及访问限制仍可能造成波动。
